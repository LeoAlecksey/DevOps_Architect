# Подсказки к лабораторной M0

> Фаза C · Статус: **Draft** · 2026-11-11
> Три уровня на каждый этап. Открывайте по одному и только когда упёрлись. Полного решения здесь нет.

Прежде чем открывать подсказку, сформулируйте для себя: что именно не получается и что вы уже пробовали. Половина проблем решается на этом шаге.

---

## S1. Замеры

**Уровень 1.** Все цифры уже есть у ядра. Вопрос не в том, где их взять, а в том, какой файл или утилита отвечает на какой из ваших вопросов. Для каждого пункта задайте себе: что именно я хочу узнать и что в этом выводе мне это скажет?

**Уровень 2.** Для памяти и swap смотрите `free`, `/proc/meminfo` (поле `MemAvailable`) и `vmstat`. Давление ядро пишет в `/proc/pressure/`. Процессор покажет `lscpu`. Свободное место нужно смотреть по тем путям, куда будут писать Docker и гипервизор, а не по корню: `df` принимает путь. Версию cgroup можно узнать по типу файловой системы, смонтированной в `/sys/fs/cgroup`.

**Уровень 3.** «Рабочий режим» значит с открытыми браузером и IDE, а не на только что загруженной системе. Снимите замеры два раза и запишите оба. Доступность источников проверяйте запросом с вашего компьютера к каждому: код ответа скажет больше, чем открытая вкладка браузера (подойдёт `curl -I`). Если репозиторий Docker или Docker Hub недоступны, подумайте заранее про зеркало.

## S4a. Репозиторий и подпись

**Уровень 1.** Подпись состоит из трёх частей: ключ, настройка Git, которая включает подпись, и файл со списком ключей, которым вы доверяете. Если не работает, ищите, какая из трёх частей не на месте. Отдельно подумайте, где окажется приватный ключ и как гарантировать, что он не попадёт в репозиторий.

**Уровень 2.** Ключ создаёт `ssh-keygen` (подойдёт `ed25519`), парольная фраза обязательна. В Git нужны параметры `gpg.format`, `user.signingKey`, `gpg.ssh.allowedSignersFile`, а автоматическую подпись включают `commit.gpgSign` и `tag.gpgSign`. Remote без рабочих файлов создаёт `git init --bare`, подключается он через `git remote add`. `.gitignore` нужно писать до первого коммита.

**Уровень 3.** Строка в `allowed_signers` состоит из имени (любого, например адреса), необязательных параметров (разумно ограничить ключ пространством имён `git`), типа ключа и самого публичного ключа. Проверять подпись можно через `git log --show-signature`, коммиты и теги по отдельности — `git verify-commit` и `git verify-tag`. Если Git пишет, что подписать не может, прочитайте ошибку целиком: чаще всего неверный путь к ключу или ключ с парольной фразой не загружен в `ssh-agent`. Чтобы убедиться, что в истории нет секретов, посмотрите не только текущие файлы, но и все коммиты, включая старые ветки.

## S2. Гипервизор и тестовая VM

**Уровень 1.** Идите по порядку: хост готов → образ настоящий → VM создана → доступ только по ключу → снимок работает. Не перескакивайте. Если упираетесь, определите слой: это хост, образ, cloud-init или сеть.

**Уровень 2.** Готовность хоста проверяет `virt-host-validate qemu`. Образ сверяйте способом издателя. Для Ubuntu это подписанный файл с суммами: сначала подпись файла, потом суммы образа (`gpg`, `sha256sum`). Опции cloud-init в `virt-install` зависят от версии, список покажет `virt-install --cloud-init=help`. Состояние VM — `virsh list --all`. Снимки делает и откатывает `virsh` (`snapshot-create-as`, `snapshot-revert`).

**Уровень 3.** В cloud-init есть настройки, которые добавляют ключ пользователю и отключают вход по паролю, ищите их в документации cloud-init (`ssh_authorized_keys`, `ssh_pwauth`). Проверка отказа по паролю должна быть настоящей попыткой входа, а не чтением конфига. Для опыта с памятью подойдёт любая программа внутри гостя, которая занимает память; на хосте смотрите резидентную память процесса QEMU вашей VM (например, через `ps`). Если вы получили не тот результат, что ожидали, запишите его как есть, это нормально.

## S3. Docker

**Уровень 1.** Разложите `daemon.json` по темам из задания: логи, адреса, доступ по сети. Для каждой темы найдите в документации `dockerd` соответствующий ключ. Затем подумайте, как вы докажете, что настройка действительно применилась, а не просто записана в файле.

**Уровень 2.** Логи: `log-driver` и `log-opts` (в них `max-size` и `max-file`). Адреса: `bip` и `default-address-pools` (у каждого пула есть `base` и `size`). Если ключа `hosts` в файле нет, демон по TCP не слушает, проверьте это через `ss -tlnp`. Применённые настройки: логирование смотрите в настройках нового контейнера (`docker inspect`), подсети — в `docker network inspect` и `ip route`. После правки демон нужно перезапустить, а контейнеры, созданные раньше, ротацию не получат.

**Уровень 3.** Перед перезапуском убедитесь, что файл — корректный JSON, иначе демон не поднимется. Подсети выбирайте, сначала выписав все занятые: сеть гипервизора, домашняя, рабочая и всё, что ещё может появиться. Опыт с firewall: опубликуйте порт на всех интерфейсах и обратитесь к нему с другого устройства, потом опубликуйте тот же порт только на `127.0.0.1` и повторите. Файл в репозитории должен совпадать с `/etc/docker/daemon.json`: подумайте, что здесь копия, а что источник истины, и как не допустить расхождения.

## S5. Скрипт управления

**Уровень 1.** Начните не с кода, а с таблицы: для каждого поля схемы `status.schema.json` запишите, откуда вы его возьмёте. Только потом пишите. Пишите `status` как набор небольших кусков, каждый отвечает за один раздел.

**Уровень 2.** Данные: `free -m`, `df`, `nproc` для хоста; `docker info --format` для Docker; `virsh list --all` для VM; `docker compose` для тестового проекта. JSON не собирайте склейкой строк: в Bash для этого есть `jq`, в Python стандартный модуль `json`. Линтеры: `shellcheck` для Bash, `ruff` для Python.

**Уровень 3.** `up` и `down` должны сначала посмотреть на состояние, а потом действовать: тогда повторный запуск безопасен. `down` должен приводить к такому состоянию, которое `status` покажет как остановленное, поэтому проверяйте связку между ними на деле: запустите `down`, потом `status --json`. Помните про коды возврата: скрипт, который в случае ошибки возвращает 0, сломает любые проверки, в том числе ваши.

## S6. Самопроверка

**Уровень 1.** Если V1 зелёный, а V2 красный, лаборатория работает за счёт того, чего нет в репозитории. Ваша задача найти разницу, а не заставить V2 замолчать.

**Уровень 2.** Начните с `git status` и `git diff`: незакоммиченное видно сразу. Потом сравните то, что лежит в системе, с копией в репозитории (`diff`). Bundle делает `git bundle create файл --all`, целостность проверяет `git bundle verify`. Проверьте, что все пути из `.course/manifest.yaml` существуют именно в коммитах, а не только на вашем диске (`git ls-files`).

**Уровень 3.** Пройдите по списку: нет ли в репозитории чего-то, чего не должно быть (ключи, токены); подписаны ли все коммиты; совпадают ли значения в манифесте и в ADR с тем, что стоит в системе; влита ли ветка изменения `daemon.json` через merge. После исправления делайте новый bundle, а не используйте старый.

## S7. Слепой отказ

**Уровень 1.** Не угадывайте причину. Сначала зафиксируйте симптом: что именно перестало работать, когда вы это заметили, что менялось перед этим. Только потом гипотеза. Запишите хронологию, она пойдёт в postmortem.

**Уровень 2.** Начните с общих сигналов: состояние служб (`systemctl status`, `journalctl -u имя`), сети и порты (`ss -tlnp`, `ip route`), диск (`df`, `docker system df`), гипервизор (`virsh list --all`, `virsh net-list --all`), Git (`git status`, `git log --show-signature`, `git reflog`). Сравнивайте текущее состояние с тем, что записано в репозитории: расхождение само по себе подсказка.

**Уровень 3.** Чинить надо так, чтобы источником истины остался репозиторий: изменение вносится в файл репозитория, коммитится подписанным коммитом и применяется оттуда, а не правится только на машине. Если вы вернули работу, проверьте, что ничего не потеряно и в remote, и локально. В postmortem отдельно отвечайте на вопросы «как это можно было заметить раньше» и «что я изменю, чтобы это не повторилось».
